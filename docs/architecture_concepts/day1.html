Load Balancing

Distributing traffic across servers — and why the balancer itself can become your biggest bottleneck.

Source: 25-Day Scaling & Architecture Series

1 The Core Concept

A load balancer sits in front of your servers and distributes incoming requests. The critical insight: it operates on network/transport data — it doesn't actually know what's happening inside your servers.

It can't see CPU usage, memory pressure, or application-level errors unless you explicitly configure health checks. This is the gap between what a load balancer appears to do and what it actually sees.

⚡ Key Insight

A load balancer can itself become a bottleneck. It's a single point through which all traffic flows — plan for its capacity, redundancy, and monitoring just like any other critical component.

2 5 Load Balancing Algorithms

🔄 Round-Robin
Requests distributed to each server in sequence. Simple and stateless. Best when servers are identical in capacity.
📊 Least Connections
New request goes to the server with fewest active connections. Ideal when request processing times vary significantly.
⚖️ Weighted Round-Robin
Like round-robin but higher-capacity servers get more requests proportionally. Use when servers have different hardware specs.
🔗 IP Hash
Client IP is hashed to consistently map to the same server. Enables session persistence (sticky sessions) without cookies.
⚡ Least Response Time
Combines active connections + response time. Routes to the server that's both least busy AND fastest responding.

3 Layer 4 vs Layer 7

Dimension Layer 4 (Transport) Layer 7 (Application)
Sees IP + TCP/UDP headers only HTTP headers, URL, cookies, body
Speed Faster — less processing Slower — full inspection
Routing logic IP + port only Path, host header, cookie, content type
SSL termination Pass-through (encrypted) Can terminate + re-encrypt
Use case High throughput, simple routing Microservices, A/B testing, auth
Examples AWS NLB, HAProxy (TCP mode) AWS ALB, Nginx, Envoy
💡 Rule of Thumb

Use L4 when you need raw throughput. Use L7 when you need routing intelligence — routing by URL path, reading auth headers, rewriting requests, or doing sticky sessions via cookies.

4 Health Checks

🟢 Active (Polling)

Load balancer proactively sends requests to servers (e.g., HTTP GET /health) on a schedule. If a server fails N checks in a row, it's marked unhealthy.

  • Catches failures immediately
  • Adds small overhead to each server
  • Configurable interval & threshold

🔵 Passive (Traffic Watching)

Load balancer monitors actual traffic responses. If a server returns too many 5xx errors or timeouts, it's marked unhealthy.

  • No synthetic traffic overhead
  • Slower to detect quiet failures
  • Misses servers receiving no traffic
✅ Production Recommendation

Use both in production. Active checks catch dead servers quickly. Passive checks detect degraded-but-alive servers that pass health checks but fail real requests.

🐢 Recovery Policy: Slow-Start

When a server comes back online after a failure, don't immediately send it full traffic. Use slow-start: gradually ramp up traffic over 30-120 seconds.

Without slow-start: server warms up JVM/caches/connections while handling 1/3 of all traffic → cascading failure.

5 Production Checklist

1
Know Your Traffic Profile

Measure peak RPS, request duration distribution, geographic origin. This determines everything else.

2
Pick the Right Layer

L4 for raw throughput and simplicity. L7 for routing intelligence, SSL termination, and microservices.

3
Configure Health Checks

Set up both active polling AND passive traffic monitoring with appropriate thresholds and intervals.

4
Monitor the Balancer Itself

Track connection count, error rate, latency on the LB. It can become the bottleneck — treat it like any critical service.

5
Revisit Every 6 Months

Traffic patterns change. Review algorithm choice, capacity, and health check thresholds regularly.

⚠️ Watch Out

The load balancer itself can become a bottleneck. It is a single point through which ALL traffic flows. Plan for active-active LB pairs, monitor its metrics, and stress-test it separately.
