Table Partitioning

The tool that dropped an 8-second query to 200ms and made a team abandon their sharding plans entirely.

1 The Origin Story

A team had a 400 million row orders table. Queries were grinding. They were planning a full sharding migration — weeks of work, high risk, irreversible.

Someone suggested trying partitioning first.

8-second query → 200ms. Sharding plans shelved entirely.

💡 Core Lesson

Partitioning is often the step that gets skipped in the rush to shard. It's lower risk, reversible, and solves the same problem for most teams at scale.

2 What Is Partitioning?

Partitioning = splitting a large table into smaller pieces WITHIN THE SAME DATABASE. One logical table, multiple physical storage units.

✅ What stays the same

  • Same database server
  • Same backup process
  • Same connection pool
  • JOINs still work
  • Transactions still work
  • App code stays the same

⚡ What you gain

  • Queries skip irrelevant partitions (pruning)
  • DROP PARTITION = ms vs DELETE = hours
  • Smaller indexes = faster maintenance
  • Parallel query across partitions
  • Hot/cold data separation

📊 Example: Orders Table

orders (logical table)
├── orders_2023
├── orders_2024
└── orders_2025 (hot!)

App queries orders — DB routes to right partition automatically.

3 The 3 Partition Types

📅 Range Partitioning

Split by a range of values — most commonly by date.

orders_2023 → Jan–Dec 2023
orders_2024 → Jan–Dec 2024
orders_2025 → Jan–Dec 2025
✅ Range queries fast (pruning) ❌ Hotspot: current month ✅ Archive old data easily

Best for time-series, billing, event logs. The most common pattern.

🌍 List Partitioning

Split by specific discrete values — categories, countries, statuses.

orders_india → country='IN'
orders_us → country='US'
orders_eu → country IN ('DE','FR','GB')
✅ Country-filtered queries fast ❌ Uneven partition sizes ⚠️ New values need new partition

Good for regional data isolation and compliance (GDPR data residency).

🔢 Hash Partitioning

Split by hash(key) % N partitions — purely for even distribution.

hash(user_id) % 4:
partition_0, partition_1,
partition_2, partition_3
✅ Even distribution ✅ Reduces lock contention ❌ Range queries scan ALL partitions

Good for high-write tables where lock contention is the bottleneck.

5 Partition Pruning — How It Works & When It Breaks

Partition pruning = when your WHERE clause matches the partition key, the database engine skips all irrelevant partitions. This is the entire reason partitioning works.

✅ Pruning Works When

  • WHERE clause includes the partition key directly
  • Data types match exactly (no implicit casts)
  • Range comparison: BETWEEN, >=, <=
WHERE created_at >= '2024-01-01'
AND created_at < '2025-01-01'

❌ Pruning Breaks When

  • No partition key in WHERE clause
  • Type mismatch (string vs int partition key)
  • Function applied to the partition key
WHERE EXTRACT(YEAR FROM created_at) = 2024
-- ❌ function breaks pruning!
⚠️ How to Verify

Run EXPLAIN on your query. Look for "Partitions pruned" or check which partitions are scanned. If all partitions appear, pruning is broken for that query.

6 When Partitioning Helps — and When It Doesn't

✅ Partitioning HELPS

  • Large tables with time-based queries — partition pruning kicks in massively
  • Data retention — DROP PARTITION takes milliseconds vs DELETE taking hours on 400M rows
  • Index maintenance — smaller per-partition indexes are faster to build/maintain
  • Parallel query execution — each partition can be processed by a different CPU core
  • Hot/cold data separation — move old partitions to cheaper storage

❌ Partitioning Does NOT Help

  • Queries don't filter on partition key — all partitions scanned anyway
  • Small tables (<10M rows) — overhead not worth it, good indexes sufficient
  • Cross-partition joins frequently needed — can be slower than unpartitioned
  • As a substitute for proper indexing — add indexes first

7 Implementation Tips

📅 Start with Monthly/Yearly

Don't partition by day — too many partitions, management overhead. Monthly or yearly is the sweet spot for most apps.

📊 Sweet Spot: 1M–100M Rows

Per partition. Too small = overhead not worth it. Too large = still slow. Aim for this range per partition.

🔮 Create Future Partitions in Advance

Use pg_partman to automatically create future partitions. Don't let inserts fail because December's partition doesn't exist yet.

🗝️ Include Key in PRIMARY KEY

In PostgreSQL, the partition key must be included in the primary key constraint. Plan your schema accordingly.

📈 Monitor Partition Sizes

Watch for partition skew — one partition shouldn't have 10× more data than others. Indicates a bad partition key choice.

🚫 Don't Mix Strategies

Don't combine range + hash on the same table (sub-partitioning is complex). Pick one strategy and stick with it.

8 Decision Framework

Situation Action Reason
<10M rows Don't partition Good indexes are sufficient. Partitioning adds complexity without benefit.
10M–500M rows, time-based queries Range partition by month/year Pruning effect is massive. Drop old partitions trivially. The canonical use case.
10M–500M rows, filtered by category/country List partition Isolate data by discrete values. Good for compliance/regional requirements.
High-write, lock contention is the problem Hash partition Distributes writes across partitions, reducing lock contention.
>500M rows, partitioning exhausted Consider sharding Now you've truly exhausted the simpler option. Sharding is justified.
