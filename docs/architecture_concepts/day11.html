Message Queues

Queues don't make systems faster — they make failure graceful. Turn an uncontrollable spike into a controllable stream.

1
The healthcare.gov Disaster
Real World · 2013

healthcare.gov launched October 2013. 250,000 users hit simultaneously. System capacity: 1,000. Crashed within minutes. Stayed broken for weeks. Final cost: $600 million.

One pattern — a properly implemented queue — could have prevented the worst of it. Instead of rejecting 249,000 users with errors, a queue would have accepted every request, returned "we'll process your application shortly", and worked through the backlog at its own pace.

2
Core Concept
Key Insight

A queue = API accepts request, drops it into a queue, returns "accepted" immediately. Work happens in the background at its own pace. The queue doesn't make your system faster — it makes failure graceful.

The uncontrollable spike becomes a controllable stream. The dam analogy: a dam doesn't make water flow faster — it controls the rate.

3
3 Components + 4 Benefits

Producer

Creates messages and publishes to the queue. Doesn't know or care who processes them. Decoupled from consumers completely.

Queue (Buffer)

Holds messages, persisted to disk for durability. Acts as the buffer between producers and consumers. Messages stay until acknowledged.

Consumer

Pulls messages, processes them, sends acknowledgment. If processing fails before ACK, message returns to the queue automatically.

4 Things Queues Give You

① Decoupling

Producer doesn't know consumers exist. Add, remove, or change consumers without touching the producer. Services evolve independently.

② Load Leveling

The dam on a river. 10,000 requests/sec spike becomes 500 req/sec steady stream through the queue. Consumer processes at sustainable pace.

③ Retry & Reliability

Unacknowledged message goes back to the queue automatically. No message lost if consumer crashes mid-processing.

④ Processing Guarantees

Choose between at-most-once, at-least-once, or exactly-once delivery semantics based on your reliability requirements.

4
Processing Guarantees
Guarantee Behavior Trade-off Example Systems Production Use
At-most-once Message delivered 0 or 1 time. No retry. Fast Possible Loss Redis pub/sub Metrics, fire-and-forget logs
At-least-once Message delivered 1+ times. No loss but possible duplicates. Reliable Duplicates Possible SQS, RabbitMQ (default) ✅ Production default + idempotent consumers
Exactly-once Message delivered exactly 1 time. No loss, no duplicates. Hard Expensive Kafka (with transactions) Financial transactions, billing
Production Reality

Production systems almost universally use at-least-once + idempotent consumers. Exactly-once is theoretically nice but operationally painful and slow. Design your consumers to handle duplicates gracefully instead.

Quick Decision Framework

📋 Task queue for background jobs → RabbitMQ or SQS Standard
📺 Event streaming + replay + multiple consumers → Kafka
🚫 Don't want to manage infrastructure → SQS (always)

6
3 Production Gotchas

① Backpressure

Monitor queue depth continuously. Alert when queue depth exceeds threshold. Auto-scale consumers when depth rises. Reject at source if queue is dangerously full — better to fail fast than let the queue become unbounded memory.

② Dead Letter Queues (DLQ)

After 3–5 failed attempts, move the message to a separate DLQ instead of retrying forever. EVERY production queue needs a DLQ. Without it, poison messages retry infinitely and block the queue. Use DLQ for alerting, inspection, and eventual replay.

③ Idempotent Consumers

Store message ID before processing. Check if already processed. Use DB upserts. Design naturally idempotent operations. "set balance to X" is safe to repeat. "add X to balance" is dangerous. At-least-once delivery means duplicates will happen.

7
When to Use (and Not)
✅ Use a Queue When
  • Work doesn't need immediate completion
  • Producer and consumer have different throughput needs
  • Need to decouple services for independent scaling
  • Reliability is critical on the processing path
  • Need to absorb unpredictable traffic spikes
❌ Don't Use a Queue When
  • User needs immediate synchronous response
  • Queue overhead isn't worth the added complexity
  • You need strong consistency guarantees
  • Using it to avoid fixing the actual bottleneck
Best Pattern

Synchronous for the fast path: validate payment, create order, return confirmation in 500ms.
Queued for everything else: send email, record analytics, notify warehouse, trigger ML pipeline.

Quick Reference
📋 Message Queues Cheat Sheet
3 Components Producer → Queue → Consumer. Queue persisted to disk. Unacked = retry.
4 Benefits Decoupling, Load leveling, Retry/Reliability, Processing guarantees.
Processing Guarantees At-most-once (Redis). At-least-once (SQS/RabbitMQ). Exactly-once (Kafka+transactions).
Production Standard At-least-once + idempotent consumers. Store msgId, check before processing.
RabbitMQ Push-based. Msgs deleted after ACK. Task distribution. Low latency.
Kafka Pull-based. Msgs RETAINED. Multiple consumers. Replay. Millions msg/sec.
SQS Managed. No servers. Standard (at-least-once) or FIFO (exactly-once).
DLQ Rule After 3–5 failures → dead letter queue. EVERY queue needs a DLQ.
Backpressure Monitor depth. Alert threshold. Auto-scale consumers. Reject if full.
