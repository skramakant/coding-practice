Fault Tolerance

Fault tolerance is about what happens after failure starts, not preventing failure. The same bug: brief error in one system, 2-hour outage in another. Difference is architecture.

1
The CrowdStrike Lesson
CrowdStrike · July 19, 2024

A Windows driver bug. One file. One update. 8.5 million machines crashed. Delta cancelled 7,000 flights. Hospitals turned patients away. Sky News went off air mid-broadcast. Total damage: $10 billion. Global impact from a single point of failure with no fault tolerance in the update pipeline.

The Key Insight

Fault tolerance isn't about preventing failure — it's about limiting blast radius after failure starts. The same bug can mean a brief error in a well-designed system or a 2-hour platform outage in a poorly-designed one. The difference is architecture.

2
4 Patterns
⏱

1. Timeouts

Cheapest fix in the resilience playbook. Most libraries have no default timeout. One slow dependency without a timeout = 5 services down.

⚡

2. Circuit Breakers

Stop calling a dead service. Fail fast, give the downstream service time to recover, test with probes.

🚢

3. Bulkheads

Isolate thread pools per dependency. Analytics hanging doesn't kill payments. Total outage becomes partial degradation.

🔄

4. Retries with Backoff

Naive retries cause retry storms. Exponential backoff + jitter spreads load and gives the system breathing room.

1
Timeouts
The cheapest fix in the resilience playbook
💣 Without Timeouts

Payments API starts hanging (30s). 100 connections all stuck. New requests queue up. Memory fills. Service starts rejecting. Upstream services fail too. One slow dependency = 5 services down.

⚠ Most Libraries Have No Default Timeout

Python requests, Java HttpURLConnection, Node fetch, Go http.Client — all have NO default timeout. You must set them explicitly everywhere.

Timeout TypeValueReason
Connect timeout 1–3 seconds TCP handshake normally takes milliseconds. If it takes 3s, the server is unreachable.
Read timeout (internal) 1–5 seconds p99 latency + buffer. Internal services should respond fast.
Read timeout (external) 10–30 seconds Third-party APIs may be legitimately slower.
Total timeout < caller's timeout Timeout budget must cascade properly. Never exceed the upstream caller's timeout.
Set Timeouts Everywhere

HTTP clients · DB clients · Cache clients (Redis) · Message brokers · Internal RPC (gRPC/Thrift). Audit your codebase this week — it's free and high-leverage.

2
Circuit Breakers
Stop working hard to accomplish nothing
💣 The Problem

Payments API completely down. Every call times out after 3s. 1,000 rps fires 1,000 doomed calls/second. Each holds a thread for 3s. You're burning resources and making recovery harder for the downstream service.

ParameterRecommended ValueNotes
Trip threshold50% failure rateOver 10s rolling window, minimum 20 requests
Open duration30–60 secondsLong enough for downstream to recover
Half-open probe1–3 requestsTest recovery without full load
Libraries

Resilience4j (Java) · Polly (.NET) · gobreaker (Go) · pybreaker (Python) · Service mesh handles it at the network layer (Istio, Linkerd)

3
Bulkheads
Turn total outages into partial degradations

Thread Pool Sizing Formula

threads = (expected_throughput × p99_latency) × 1.5

Example: 50 rps × 0.5s p99 = 25 in-flight. +50% headroom = 40 threads.

Also Applies To

  • Connection pools — slow analytics queries don't starve transaction connections
  • Process isolation — memory leak in one process doesn't crash the others
4
Retries with Exponential Backoff + Jitter
Avoid turning recovery into a DDoS attack
💣 Retry Storm

1,000 clients hit overwhelmed API. Get errors. Retry immediately. Now 2,000 rps. Some fail. Retry again. 3,000 rps. Then 4,000. AWS S3 February 2017: S3 had an outage. Every service relying on S3 retried aggressively. The retry traffic prevented recovery.

Exponential Backoff

Delay doubles each attempt: 100ms → 200ms → 400ms → 800ms (capped at 10s). Gives the downstream service exponentially more time to recover between attempts.

Jitter (Critical)

Without jitter: all 1,000 clients retry at exactly the same moment → synchronized thundering herd.
With jitter: retries spread randomly across a window → load smoothed out.

Cap Retries at 3

Past 3 retries you're DDoSing, not retrying. Only retry idempotent operations — POST "create order" might have succeeded but the response got lost.

Libraries

Tenacity (Python) · Polly (.NET) · Resilience4j (Java) · retry-go (Go) · AWS/GCP/Azure SDKs have built-in exponential backoff

3
Build In This Order
SPRINT 1

① Timeouts Everywhere

Cheapest, highest leverage. Audit all HTTP clients, DB clients, cache clients, message brokers, internal RPC. One afternoon's work.

SPRINT 1-2

② Bulkheads for Top 3 Dependencies

Identify your top 3 highest-traffic dependencies. Size thread pools properly. Isolate them from each other.

SPRINT 2

③ Circuit Breakers on External Calls

Wrap all external service calls with circuit breakers. Start with the most critical and highest-failure-rate dependencies.

SPRINT 2-3

④ Backoff on Every Retry

Every retry in the codebase should use exponential backoff + jitter. Find them all. Replace naive time.sleep(1) patterns.

Step 5: Chaos Test It

Once patterns are in place, validate them by intentionally injecting failures. Tools: Gremlin, Chaos Monkey (Netflix), Litmus (Kubernetes). If you haven't tested failure mode, you don't know if it works.

"Design for failure and resilience follows. Design for success and you'll be writing postmortems instead of features."

Quick Reference
📋 Fault Tolerance Cheat Sheet
Timeouts — Values Connect: 1-3s. Read (internal): 1-5s. Read (external): 10-30s. Total < caller's timeout.
Timeouts — Set Everywhere HTTP, DB, cache, message broker, gRPC/Thrift. No library has a default. Audit now.
Circuit Breaker States Closed (normal) → Open (fail fast, microseconds) → Half-Open (test 1-2 probes).
Circuit Breaker Tuning Trip at 50% failures over 10s window (min 20 requests). Open 30-60s. 1-3 probes.
Bulkhead Formula threads = throughput × p99_latency × 1.5. Example: 50rps × 0.5s × 1.5 = 40 threads.
Retry Formula delay = min(10s, 100ms × 2^attempt) + random(0, 100ms). Cap at 3 retries.
Retry Storm Prevention Jitter = critical. Without it all clients retry simultaneously. With it, load spreads.
Only Retry Idempotent Ops GET, DELETE (usually safe). POST "create order" may have succeeded silently.
Build Order 1) Timeouts · 2) Bulkheads · 3) Circuit breakers · 4) Backoff · 5) Chaos test.
