Database Scaling

Database scaling is a sequence. Each step is ~10x cheaper than the next and handles ~10x more load. Apply steps in order. Most products never reach step 5.

1
The Premature Sharding Story
Happens Hundreds of Times a Year

A growing startup notices dashboards slowing from 200ms to 4s. On-call gets paged at 11pm — 95% CPU. Someone says "we need to shard". A 2-week sprint becomes a 4-month migration. Halfway through the sharding implementation, they discover the original problem: one missing index on created_at. The entire 4-month effort was unnecessary.

The Principle

Database scaling = a sequence. Each step is roughly 10x cheaper than the next and handles roughly 10x more load. Identify the actual bottleneck. Apply the cheapest fix first. Move on.

2
The 5-Step Scaling Ladder
1
Indexes
Most underrated tool in the database. Free to add.
START HERE

How to Find Missing Indexes

pg_stat_statements (Postgres) or slow query log (MySQL). Optimize highest total time = avg duration × call frequency. Run EXPLAIN and look for Seq Scan (Postgres) or ALL (MySQL) on large tables.

Two Most Commonly Missing

  • Foreign keys — NOT auto-created in most DBs. Every JOIN on orders by customer needs customer_id indexed.
  • Composite indexes — status='pending' AND created_at > ? needs (status, created_at). Equality columns first, range columns last.

Index Maintenance

  • Indexes slow writes — every INSERT/UPDATE maintains all indexes
  • >15 indexes per table = probably duplicates
  • pg_stat_user_indexes shows usage — drop 0-scan indexes
The Impact

One CREATE INDEX can turn a 4-second query into a 4-millisecond query. That's a 1,000× improvement. Free to add. This is the first thing to check — always.

2
Connection Pooling
One config file. Enormous leverage.
HIGH LEVERAGE
The Problem

Each Postgres connection = ~10MB RAM + auth handshake overhead. max_connections=100 means only 100 simultaneous queries. 50 app workers × 3 servers = at the limit. 4th server = "too many connections" errors.

Without Pooling

  • 1 app worker = 1 DB connection (held for entire request)
  • 50 workers × 3 servers = 150 connections
  • At max_connections: new requests fail
  • Scale out → immediately hit DB limit

With PgBouncer

  • App → 5,000 connections to PgBouncer
  • PgBouncer → 50 connections to Postgres
  • Postgres sees 50 sessions
  • 5,000 app requests served

Two Layers

Application-side (built into ORM): pool size = CPU cores × 2–3, capped at 20–30 per instance.

External pooler: PgBouncer (Postgres), ProxySQL (MySQL). Transaction mode: connection returned to pool after each transaction.

This Has Saved Companies From Outages

PgBouncer in transaction mode: app has 5,000 connections to PgBouncer. PgBouncer holds 50 connections to Postgres. Postgres sees 50 sessions. 5,000 apps served. One config file. Enormous leverage.

3
Read Replicas
Multiply read capacity. Doesn't help writes.
50k–200k read QPS

Primary accepts writes and streams WAL log. Replicas apply changes continuously. Replicas serve reads only — never accept writes.

SetupHelps WithDoes NOT Help
1 primary + 2–5 read replicas Read-heavy workloads (analytics, search, list views) Write throughput — every write still hits primary
Reads via load balancer Isolating heavy read workloads from writes Storage — each replica is a full copy
Geographic replicas Low-latency reads in different regions Replication lag — reads may be stale
⚠ Replication Lag

Time between write hitting primary and appearing on replica. Usually milliseconds, sometimes seconds/minutes under heavy write load. Read-your-write inconsistency: user updates profile, reads from replica not yet caught up, sees old data. Fix: route user's own reads to primary for N seconds after a write.

4
Partitioning
Split huge tables within the same database.
5–10× on huge tables

Split one large table into smaller physical tables within the same database. The application sees one table — the DB engine queries only relevant partitions.

The Problem

10 billion row events table. Query is slow even with a perfect index — the index itself is huge. Partition by month: 24 tables of 400M rows. Query filters by date = touches only the relevant partition.

Benefits

  • 10B rows → manageable 100M–400M row partitions
  • Queries 10–100× faster on time-series data
  • Drop old data in O(1): DROP PARTITION vs hours-long DELETE
  • VACUUM runs in minutes not days

When to Partition

  • Table has a natural range column (date, created_at)
  • Queries almost always filter by that column
  • Regular data expiry needed
  • Table is too large for index to fit in memory
5
Sharding
Last resort. Permanent decisions. Massive complexity.
LAST RESORT
Only When
  • Writes have outgrown one primary
  • Read replicas don't help (bottleneck is on the write path)
  • Partitioning done but single partition is still too large
  • Dataset is multi-TB and growing

4 Hard Decisions

  • Shard key — permanent, can't change easily
  • Shard map — how to route queries to correct shard
  • Cross-shard queries — how to handle them (expensive)
  • Rebalancing — when shards grow unevenly

When You DON'T Need It

  • Haven't exhausted steps 1–4
  • Primary DB CPU under 60%
  • Haven't profiled slow queries
  • Missing indexes (see: the story at the top)

Quick Reference
📋 Database Scaling Cheat Sheet
The Sequence Indexes → Connection Pooling → Read Replicas → Partitioning → Sharding. Do not skip steps.
Indexes First Free. 4s → 4ms (1000×). Find via pg_stat_statements. EXPLAIN for Seq Scan. Always check first.
Missing Index Types Foreign keys (not auto-created!). Composite indexes: equality cols first, range cols last.
Index Hygiene Slow writes. Max ~15 per table. Drop 0-scan indexes via pg_stat_user_indexes.
Connection Pooling PgBouncer transaction mode: 5000 app → 50 Postgres. One config. Enormous leverage.
Pool Sizing App-side: CPU cores × 2-3, cap at 20-30. PgBouncer: ~50 connections to Postgres.
Read Replicas 1 primary + 2-5 replicas. Helps reads only. Watch replication lag. Route writes to primary.
Read-Your-Write Fix Route user's own reads to primary for N seconds after a write.
Partitioning Same DB server. By date/range. O(1) old data drop. 10-100× on time-series queries.
Sharding Last Resort 4 hard decisions. Shard key is permanent. Don't shard if primary CPU < 60%.
