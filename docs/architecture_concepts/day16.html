Service Discovery

Where is service X right now? Not 5 seconds ago — right now. When instances are ephemeral and deploys are constant, hardcoded addresses become a liability.

01
The Incident
2pm Tuesday — Deploy goes out

3 new payments instances come up. By 2:03pm every checkout is failing. The new instances are healthy. The old ones are dead. Hostnames moved. Nothing told anyone.

This is what happens when services depend on static addresses in a dynamic world.

The Scale Problem

  • 3 services = config file works fine
  • 5 services = env vars manage it
  • 10 services = you feel the pressure
  • 50 services = hardcoded addresses become genuinely painful

The Core Question

Where is service X right now?

Not 5 seconds ago. Not where it was at last deploy. Where is it right now, and is it healthy?

02
The Hardcoding Problem
✅ Hardcoding WORKS when
  • Static infrastructure (3 EC2 boxes with elastic IPs)
  • Deploys are infrequent and planned
  • Instances are long-lived (months, not minutes)
  • No autoscaling involved
❌ Hardcoding BREAKS when
  • Instances are ephemeral (containers/serverless/autoscaling)
  • Deploys are frequent (rolling/blue-green/canary)
  • Services scale dynamically
  • Crossing regions or clusters
⚠️ Root Causes of Hardcoding Failures
  • New instances spin up with unknown IPs
  • Old instances die without telling callers
  • Hostnames change on deploy
  • Pods rescheduled to different nodes
  • Teams rename endpoints during refactors
03
Three Approaches Compared
🌐

Approach 1: DNS-Based Discovery

Route53 · CoreDNS · Consul DNS Interface

Every service gets a DNS name. Clients resolve at call time. When instances change, update DNS records. The client calls the hostname, the OS resolves, the connection goes to the returned IP.

payments.internal.company.com → [10.0.0.42, 10.0.0.43]

✓ Strengths

  • Universally understood — every language/OS speaks DNS
  • Cacheable — DNS built to be cached, cheap lookups
  • Simple — minimal operational overhead

✗ Weaknesses

  • TTL caching — dead IPs kept until TTL expires
  • Low TTL = hammers DNS servers constantly
  • Thin protocol — IPs only, no ports/weights/health/metadata
  • No routing intelligence (can't do 90%/10% splits)
Pick When

Deploys infrequent (minutes apart or more) · Instances reasonably long-lived · Maximum simplicity needed · Already paying for managed DNS. Common pattern: DNS for discovery + load balancer in front for traffic shaping.

04
Approach 2: Registry-Based Discovery
📋

Service Registry

Consul · Eureka · etcd · ZooKeeper

A dedicated service whose only job is tracking what's running where. Instances register themselves on startup, send heartbeats, and get deregistered when heartbeats stop.

1. Instance starts → registers: "I am payments, IP 10.0.0.42, port 8080, healthy"
2. Sends heartbeat every few seconds to registry
3. If heartbeat stops → registry removes it within seconds
4. Clients query registry for healthy instance list → pick one → call it

✓ Strengths

  • Near real-time — seconds not TTL
  • Rich metadata — version, region, capacity
  • Active health checks — probes instances
  • Watches — subscribe to changes, get notified

✗ Weaknesses

  • Registry = critical infrastructure (if down, nothing finds anything)
  • Needs HA mode, backups, upgrades, monitoring
  • Client SDKs needed per language
  • Operational tax
Pick When

15+ services · Frequent deploys · Need metadata-based routing (version/region/capacity) · Have operational maturity to run another piece of infra. Consul is go-to for non-Kubernetes. Eureka from Netflix but no longer their default.

05
Approach 3: Kubernetes Platform-Native
⚓

Platform-Native Discovery

Kubernetes Services + CoreDNS + Endpoints

Platform handles discovery automatically. Create a Service object selecting pods by label. Kubernetes gives a stable virtual IP and DNS name.

payments.default.svc.cluster.local → ClusterIP → Endpoints → [Pod-A, Pod-B]

Kubernetes maintains the Endpoints object automatically. Pods come and go = Endpoints update within seconds. New pods only get traffic after readiness probes pass.

✓ Strengths

  • Zero application code — service doesn't know discovery exists
  • Integrated with deploys (rolling updates + readiness + discovery as one system)
  • Free — already running K8s

✗ Weaknesses

  • Platform lock-in — services outside cluster can't use K8s Services natively
  • CoreDNS quirks — NDOTS, search domains, caching misconfigs caused real outages
  • Scaling limits — thousands of Services hit cluster limits (most never reach this)
Pick When

On Kubernetes AND services live inside the cluster. This is the default. Don't fight it. Don't install Consul on top of K8s "just in case."

06
Service Mesh — What It's NOT
⚠️ Common Misconception

A service mesh is NOT service discovery. It sits above discovery and uses whatever discovery you already have.

What Mesh Adds

  • Traffic management — canaries, weighted routing, A/B tests
  • Security — mutual TLS everywhere, auto cert rotation
  • Observability — per-call tracing, latency, errors without code changes
  • Resilience — circuit breakers, retries, timeouts at network layer

When to Add a Mesh

Most teams start without mesh. Add it when you have specific problems it solves — not preemptively. Complexity is significant. 8 services don't need Istio.

07
Decision Framework
1
Are you on Kubernetes? Yes → K8s-native, done. Stop here.
2
How dynamic is your infrastructure? Static (deploys rare, instances long-lived) → DNS. Dynamic (deploys multiple times/day, autoscaling) → Registry.
3
Need metadata-based routing? Yes → Registry. DNS can't give you "only v2 instances in us-east-1" — DNS returns IPs only.
Approach Best For Tools Routing Intelligence Operational Cost
DNS Static infra, simple needs, low deploy frequency Route53, CoreDNS None (IPs only) Low
Registry 15+ services, dynamic infra, metadata routing Consul, etcd Rich Medium-High
K8s Native On Kubernetes, in-cluster services K8s Services, CoreDNS Via kube-proxy Free (built-in)
08
What to Avoid
❌ Anti-Patterns
  • Don't roll your own — subtle correctness issues: stale data, split-brain, race conditions
  • Don't pick based on what Netflix uses — their problems aren't your problems. Netflix-scale issues don't apply to you yet
  • Don't combine 3 mechanisms — K8s for some services, Consul for others, hardcoded for the rest = maintenance nightmare
  • Don't add service mesh too early — 8 services don't need Istio. Add it when you have specific problems it solves
  • Don't fight your platform — if you're on K8s, use K8s Services. Don't install Consul on top just in case
09
Quick Reference
⚡ Service Discovery Cheat Sheet
On Kubernetes? Use K8s Services + CoreDNS. Default. Done. payments.default.svc.cluster.local
Static infra, few services? DNS-based. Route53 or CoreDNS. Keep TTL reasonable.
Dynamic, 15+ services? Registry-based. Consul for non-K8s. Needs HA mode.
DNS TTL tradeoff Low TTL = fresh data, hammers DNS. High TTL = cached stale IPs after failure.
Registry heartbeat Service registers on start, heartbeats every few seconds, removed when heartbeat stops.
Service mesh ≠ discovery Mesh sits above discovery. Adds mTLS, canaries, observability. Add later, not now.
K8s readiness probes New pods only get traffic after readiness check passes. Discovery + health as one system.
Eureka status Netflix origin. Not Netflix's default anymore. Consul is the go-to for non-K8s.
