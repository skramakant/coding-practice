Consistency Models

"Consistent" is one of the most overloaded words in distributed systems. "We're strongly consistent" could mean any of 5 different things. Here's what they actually mean.

01
The Bitcoin Incident — 2013
March 12, 2013 — Bitcoin blockchain splits into two parallel realities

For 6 hours, the network ran as two separate chains. Coins spent on one chain didn't exist on the other. Then the network picked a winner and erased the other timeline. Some transactions permanently gone.

This is what consistency models look like when you can see them. The question every distributed system answers: when can I read what I wrote from another node?

Single Machine

Data in one place. Read always sees the latest write. Simple, because there's only one copy and one timeline.

Multiple Machines

Copies exist. Writes happen on one node. Reads happen on another. Network between them is slow and unreliable. Consistency becomes a design choice.

What a Consistency Model Answers
  • When can I read what I just wrote from another node?
  • Who wins on concurrent writes?
  • What happens if the network breaks mid-operation?

The Consistency Spectrum
03
The 5 Models in Detail
Model 1 — Strongest
Linearizability

Every operation appears to happen at a single moment in time, in an order that matches the real world. The system cannot reorder operations even for efficiency.

Alice writes X=5 at 10:00:00.001. Bob reads X at 10:00:00.002. Bob MUST see 5. No exceptions.
How Single primary or Raft/Paxos consensus
Cost 1-5ms local DC · 50-200ms cross-region
Partition behavior Minority side stops accepting writes
Examples: etcd, ZooKeeper, Google Spanner, FaunaDB, CockroachDB
Use when: Banking, inventory limits, distributed locks, leader elections
Model 2
Sequential Consistency

Operations from any single client appear in the order that client issued them. The order between different clients can be anything the system likes.

You issue A then B. Anyone reading sees A before B. But your writes and mine can be interleaved in any order the system chooses.
Less cost than linearizable. More academic than production. Worth knowing the term — it comes up in papers and distributed systems discussions.
Model 3
Causal Consistency

Causally related operations happen in the right order. Unrelated operations can happen in any order.

Alice posts a status. Bob comments on it. The comment is causally after the post. You always see the post before the comment. But Alice's post and Charlie's unrelated post have no causal link — they can appear in any order.
Implementation Vector clocks or session tokens to track causal relationships
Cost Real overhead but manageable. No global coordination.
Examples: COPS, some Riak configurations
Use when: Comments, messaging, social feeds, WhatsApp-like ordering
Model 4 — Weakest / Most Common
Eventual Consistency

If you stop writing and wait long enough, all replicas agree. No commitment on when. No commitment on intermediate values. No commitment on ordering.

"Eventually" = usually milliseconds, sometimes seconds, under heavy load = minutes, pathological cases = hours.
Cost Almost nothing. Each node accepts writes locally, gossips asynchronously.
Break: Read-your-writes Write X=5, immediately read X, get 4 from stale replica
Fix Sticky sessions — route user reads to node that handled their writes
Examples: DynamoDB default, Cassandra default, Couchbase, Riak, S3
Use when: Social feeds, like counts, view counts, product recommendations, search indexes — anywhere availability matters more than freshness
04
CAP Theorem & PACELC
05
Decision Framework
1
What if a read returns slightly stale data?
"User sees yesterday's like count = fine" → eventual consistency. "We double-charge a customer" → strong consistency for that path.
2
What happens during a partition?
"Keep taking orders, sort it out later" → AP. "Refuse rather than risk double-counting inventory" → CP.
3
What's your latency budget?
Strong consistency across regions = 100-200ms per write. Eventual consistency = single-digit milliseconds.
💡 Real Systems Mix Models

Same database, different per-operation settings. Shopping cart = eventual. Checkout = strong. Order history = causal. Don't set the whole system to strong "to be safe" — you pay latency everywhere for properties most operations don't need.

06
Common Traps
❌ Watch Out For
  • "We're consistent" — without specifying which kind. Linearizable? Sequential? Causal? This tells you nothing.
  • Read-your-own-write bugs — user updates their profile, refreshes, sees old data. Classic eventual consistency footgun in production.
  • "Cross-region writes completing in 5ms" — the speed of light says no. If your cross-region writes complete in 5ms, you don't have strong consistency. Something is lying to you.
  • No conflict resolution strategy — if your AP system accepts concurrent writes on both sides of a partition, what happens when the partition heals? "Last write wins" silently discards data.
07
Quick Reference
⚡ Consistency Models Cheat Sheet
Linearizability Strongest. Every op has a single point in real time. etcd, ZooKeeper, Spanner. 1-200ms cost.
Sequential Consistency Per-client ordering preserved. Global order is anything. More academic. Worth knowing term.
Causal Consistency Cause → Effect ordering only. Unrelated ops = any order. Vector clocks. COPS, Riak.
Eventual Consistency All replicas converge eventually. No timing guarantee. DynamoDB, Cassandra, S3.
CAP: CP Consistency + Partition tolerance. Minority side stops on split. Spanner, etcd, ZooKeeper.
CAP: AP Availability + Partition tolerance. Both sides keep writing, diverge. DynamoDB, Cassandra.
CAP: No CA Networks partition. Partition tolerance is not optional. "CA" is not a real option.
PACELC Extends CAP to normal ops. PA/EL (most DBs) vs PC/EC (Spanner). Latency vs consistency.
Mix models Shopping cart = eventual. Checkout = strong. Order history = causal. Per-operation is fine.
