Eventual Consistency

Eventual consistency isn't a compromise — it's a deliberate engineering choice. DynamoDB is eventually consistent by default. Most teams never pay for strong consistency. Here's why, and when to change that.

01
The Deliberate Choice
DynamoDB — Eventually Consistent by Default

DynamoDB is eventually consistent by default. You can pay for strong consistency — it costs 2x and adds latency. Most teams never turn it on. Not because they don't care about consistency, but because 2x cost and extra latency aren't worth it for most data.

The Mental Model Shift

Eventual consistency = deliberate engineering choice, not a compromise. The question is not "should I be consistent?" — the question is "what does consistency cost me here, and do I need to pay it?"

03
Where Eventual IS the Right Choice
✅ Good Fits for Eventual Consistency

🐦 Social Feeds

A slightly delayed like count is invisible to users. An unavailable feed is not. Availability wins here. Nobody notices if the count is 2 seconds stale.

🛍️ Product Catalogs & Search

Showing a product that sold out 3 seconds ago is far better than refusing to show products at all. The cost of a brief stale display is low.

📊 Analytics & Metrics

View counts, click metrics, engagement numbers. Nobody makes financial decisions on this millisecond's number. Eventually consistent is perfectly fine.

🔄 Caching Layers

Redis and CDN caches are eventual by nature. The origin is the source of truth. Cache staleness is expected and designed around.

💬 User-Generated Content

Comments, reviews, non-critical profile updates. The data is not transactional. Slight delay in propagation is acceptable.

04
Where Eventual WILL Hurt
❌ Do NOT Use Eventual Here

💰 Money

Balances, charges, refunds, inventory for fulfillment. Concurrent deductions on stale reads = fraud. Two users buying the last item = negative inventory.

🔐 Identity & Access Control

Permission revokes must take effect immediately. If IAM is eventually consistent, a revoked admin token might still work for seconds after revocation. That's a security bug.

🔑 Unique Constraints

Username uniqueness, email uniqueness, inventory not going negative. Two users pick the same username simultaneously — both succeed if eventual. One of them is wrong.

🔒 Leader Election & Locks

Two nodes think they hold the same lock = split-brain. Eventual consistency and distributed locking are fundamentally incompatible.

🔗 Cross-Service Workflows

Service A writes, Service B immediately reads and finds nothing. If the workflow assumes instantaneous state propagation, eventual consistency will silently break it.

05
Conflict Resolution Strategies
⚠️ The LWW Warning

Most systems default to Last-Write-Wins because it's simple. Most production incidents involving eventual consistency involve LWW silently discarding data. The losing write is just gone — no error, no log entry, no indication anything was lost.

06
Practical Patterns for Eventual Consistency

🔑 Idempotent Writes

Same write twice = no-op. Use idempotency keys. Store key + result. Duplicate key = return stored result. Prevents double-processing on retries.

POST /charge {idempotency_key: "ord-123"}

📝 Versioned Writes

Every write includes a version or conditional check: "only apply if current version is X." DynamoDB condition expressions, Cassandra lightweight transactions.

ConditionExpression: version = :expected

↩️ Compensating Actions

When you can't make multi-step operations atomic, design the inverse operation. Payment failed after inventory reserved = release inventory. Core of the Saga pattern.

📈 Observability on Lag

Track replication lag as a first-class metric. Alert when it exceeds tolerance (usually 1-5s for user-facing, longer for analytics). If you can't see lag, you can't debug consistency bugs.

Opting Into Strong Consistency
Database How to Enable Strong Cost Granularity
DynamoDB ConsistentRead=true 2x read cost Per-request
Cassandra Consistency level: ONE / QUORUM / ALL Latency overhead Per-query
Cosmos DB 5 consistency levels (Strong, Bounded Staleness, Session, Consistent Prefix, Eventual) Higher RU cost Per-account or per-request
💡 The Rule

Default to eventual. Opt into strong for specific operations that need it. Shopping cart = eventual. Checkout that charges the card = strong. Don't set the whole system to strong "to be safe" — you pay the latency and cost tax everywhere for properties most operations don't need.

Quick Reference
⚡ Eventual Consistency Cheat Sheet
Read-Your-Writes guarantee Your session always sees your own writes. Sticky sessions or primary-read-after-write routing.
Monotonic Reads guarantee Once you've read version N, never see version <N. Session tracks max version seen.
Causal in Session A → B in your writes means readers seeing B also see A. No orphaned replies.
LWW danger Last-Write-Wins silently discards data. Most eventual consistency incidents trace back to LWW.
CRDTs Counters/sets/maps with deterministic merge. No app logic needed. Riak, Redis, Automerge.
Idempotency keys Store key + result. Duplicate write returns stored result. Prevents double-processing.
Good fit: feeds, catalogs, analytics Availability > freshness. Slight staleness invisible to users.
Bad fit: money, auth, unique constraints Strong consistency required. Concurrent eventual writes = fraud / split-brain / duplicates.
Replication lag observability Track lag as first-class metric. Alert at 1-5s user-facing. Can't debug what you can't see.
