Distributed Transactions

A European bank spent 18 months building a distributed transaction system. It took 4 months to rip out and replace with sagas. The lesson cost 2 years. Here's what they learned so you don't have to.

01
The 2-Year Lesson
European Bank, 2017

18 months building a distributed transaction system across 12 microservices. Every payment required 2PC spanning 4 databases. Under load, the coordinator became a bottleneck. Under network partitions, transactions hung for minutes.

Eventually ripped out and replaced with sagas. The rewrite took 4 months. The lesson cost 2 years.

What Is a Distributed Transaction?

An operation that needs to succeed or fail as a unit across more than one database or service.

Classic example: place order = debit account + reserve inventory + create order record + send confirmation. If any step fails, ALL must roll back.

Single DB vs Multi-Service

Single DB: BEGIN, do work, COMMIT or ROLLBACK. ACID. Done.

Multiple services with different DBs: No shared coordinator, no shared storage, network between them is unreliable. Need something fundamentally different.

02
Why Distributed Transactions Are Hard
Failure Modes That Don't Exist in Single-DB
  • Participant votes yes, then crashes before applying the commit
  • Coordinator crashes after collecting votes but before sending the decision
  • Network partition leaves some committed and others uncertain
  • Locks held during protocol block other work for seconds or minutes
  • No single coordinator unless you introduce one — and that coordinator is a new SPOF
  • Each service has its own failure modes; network can separate coordinator from participant mid-transaction

Saga Pattern — The Practical Alternative
⚠️ What Sagas Do NOT Give You

ISOLATION. Between step 1 and step 3, another transaction can observe a debited account with no order yet created. Design around this: make intermediate states explicit (order_status: pending_payment), ensure readers handle in-progress workflows, use timeouts and cleanup jobs.

05
Outbox Pattern — Making Saga Steps Reliable
💡 Why Outbox is High-Leverage

Business update + outbox write = one local transaction. Either both happen or neither. No lost events. No need for distributed coordination. The relay process can crash and restart — it just re-reads from the outbox. This is one of the highest-leverage patterns in distributed systems.

06
Decision Framework
1
Can this workflow live in a single database? Yes → put it there. One ACID transaction. Done. This is the best outcome. Don't split services just to split them.
2
Must cross services — can you use a saga? Model the steps. Write compensating actions. Use an orchestrator. Add outbox for reliable event publishing. Handles the vast majority of cases.
3
Saga not viable — justify 2PC? Use a proven coordinator. Keep participant count very low (2-3). Measure latency impact. Plan for coordinator failure scenarios explicitly.
4
None of the above work? Reconsider service boundaries. A workflow requiring tight multi-service transactions often means the services are split in the wrong place. Merging back is sometimes the correct answer.
Approach Isolation Latency Failure Model When to Use
Single DB ACID Full ACID Low (5ms) Local, recoverable from WAL When all data in one DB — ideal
Saga (Orchestrated) None (intermediate visible) Low per step Compensating actions on failure Multi-service workflows (most cases)
2PC Full atomicity High (50-200ms) Coordinator crash = hung transactions 2-3 participants, infrequent, critical
07
Common Traps
❌ Anti-Patterns
  • Don't hand-roll a transaction coordinator. The edge cases in distributed consensus are subtle and brutal. Use proven implementations.
  • Compensating action failures must be handled. What if the compensation fails? Need retry + dead letter queue + manual intervention path.
  • 2PC doesn't mean zero risk. Heuristic decisions after coordinator failure can still produce divergence. There is no perfect protocol.
  • Don't use distributed transactions to paper over bad service boundaries. If you constantly need tight transaction coordination across services, the services may be wrong split.
  • Don't forget the outbox. Service commits local tx then crashes before emitting event = permanently stalled workflow with no visible error.
08
Quick Reference
⚡ Distributed Transactions Cheat Sheet
First choice: single DB If all data can live in one DB, use ACID. Don't distribute what doesn't need to be.
Second choice: Saga Local transactions + compensating actions. No distributed locks. Works across services.
Saga coordination Orchestration > Choreography for anything non-trivial. Easier to observe and debug.
Saga lacks isolation Intermediate states visible. Make them explicit: status: pending_payment
Outbox pattern Write event to outbox IN SAME TRANSACTION as business update. Relay publishes separately.
2PC: when to use 2-3 participants, same DC, infrequent operations, correctness critical, latency tolerable.
2PC failure mode Coordinator crashes after phase 1 → all participants stuck holding locks indefinitely.
Compensating actions Must handle their own failures. Retry + DLQ + manual intervention. Can't be fire-and-forget.
Reconsider service boundaries If you always need tight cross-service coordination, services might be split wrong.
