Content Delivery Networks

A CDN is a network of servers in cities worldwide. The real magic is protection from origin overload — not just faster speeds for end users.

Source: 25-Day Scaling & Architecture Series

1 What a CDN Actually Is

A CDN is a geographically distributed network of servers (called Points of Presence or PoPs) placed in cities worldwide. When a user requests content, DNS/GeoDNS automatically routes them to the nearest PoP.

Most teams think of CDN as "making things faster." That's true but secondary. The primary value is absorbing massive traffic volume so your origin servers don't have to.

⚡ The Real Magic

CDN's primary value is protection, not speed. When 92% of requests are served from edge caches, your origin only sees 8% of actual traffic — a massive buffer against traffic spikes.

3 CDN Topology

4 Pull-Based vs Push-Based CDN

⬇️

Pull-Based

95% of teams

Edge nodes fetch content from your origin on the first cache miss. Subsequent requests are served from cache until TTL expires.

  • Zero pre-warming required
  • Works automatically from day one
  • First visitor after TTL expiry gets miss
  • Best for: regular web content, APIs, images
⬆️

Push-Based

Special events

You pre-upload content to all edge nodes before requests arrive. Content is already warm when users hit the CDN.

  • Zero first-request misses
  • Must manage content lifecycle manually
  • Storage costs at all PoPs
  • Best for: game launches, live event assets, known spikes

5 Cache Invalidation Strategies

Strategy How It Works Risk Recommendation
TTL-Based Content expires after a set time (e.g., 60 seconds) Accepts staleness Use for most content. Simple and reliable.
Purge API Manually invalidate cached content on write Thundering herd risk Use with staggered TTL as safety net. Not as primary.
stale-while-revalidate Serve stale content while fetching fresh in background Minimal Best choice. Users get instant response always.

stale-while-revalidate in Practice

Cache-Control: max-age=60, stale-while-revalidate=30

Fresh for 60s → serve immediately.
60-90s → serve stale but fetch fresh copy in background.
After 90s → serve stale until fresh copy is ready (no user-visible wait).

⚠️ Thundering Herd Problem

When you purge a popular URL, thousands of requests simultaneously hit your origin before the cache is repopulated. Mitigate with:

  • Request coalescing (most CDNs do this automatically)
  • Keeping a short TTL as backup safety net
  • Staggering invalidations across edge nodes

6 Edge Computing

Modern CDNs let you run compute at the edge — code that executes at the PoP closest to the user, before the request ever reaches your origin.

Cloudflare Workers
V8 isolates, runs JS/WASM. ~1ms startup. 275+ PoPs.
Lambda@Edge
AWS. Run Node.js/Python at CloudFront edge. Higher latency than Workers.
Fastly Compute
WASM-based. Strongly typed, very fast cold starts.

Common edge use cases:

Authentication / JWT validation A/B testing Geo-personalization Request rewriting Bot detection Image optimization
