Leader Election

"The cost of getting this wrong is not a mildly elevated error rate. It is divergent data, multi-day recovery, and a postmortem no one wants to write."

01
The Split-Brain Incident
2012 — Cloud Provider Network Partition

Network partition hit a database cluster. Two nodes both believed they were primary. Each accepted writes independently for hours.

Partition healed. Two divergent copies of customer data. Reconciling took days. Some updates permanently lost.

Failure mode: split-brain. When leader election fails, this is what it looks like.

Split-Brain Definition

Two nodes simultaneously believe they are the leader. Each accepts writes independently. On reconnection: two divergent histories. One must be discarded. Data is permanently lost. Recovery is manual and takes days.

02
When You Need a Leader

✅ Use Leader Election When

  • Writes must be totally ordered — single primary serializes all writes
  • Single node must own state — Kafka partition leadership
  • Coordination must not run concurrently — distributed cron jobs, failover controllers

❌ Don't Use Leader When

  • Work safely partitioned — stateless consumers processing independent tasks
  • Leaderless replication works — Dynamo-style with conflict resolution for high-availability writes
  • Simple mutual exclusion — a distributed lock with fencing may be enough
03
Core Requirements
Safety (Non-Negotiable)

AT MOST ONE leader at any time (in a given term/epoch). This cannot be relaxed. Two simultaneous leaders = split-brain = data loss.

Liveness

A leader is eventually elected if a majority can communicate. The system can pause during partitions — the minority side sits without a leader. That's acceptable. Having two leaders is not.

⚡ Fast Failover

Seconds, not minutes. Long failover windows = extended unavailability for any work requiring a leader.

🎯 Stable Leadership

Avoid flapping on transient network blips. Constant leader changes = constant disruption. Make timeout windows conservative relative to GC pauses and network jitter.

🔑 Fencing

Old leader cannot continue acting after a new leader is elected. Without fencing, a slow or partitioned old leader can still commit writes. This is the overlooked half of leader election.

04
Three Approaches
05
Fencing — The Missing Piece
🔑 The Fencing Rule — Non-Negotiable

Election alone is NOT enough. You need fencing. Without it, a slow or partitioned old leader can still commit writes after a new leader is active, causing split-brain. Every leader election design without a fencing story is incomplete.

06
Split-Brain — Root Causes

Old Leader Not Notified

Old leader never learns it was demoted after a partition. Keeps serving writes, thinking it's still in charge.

Lease Expiry Not Respected

Leader's lease expires but it doesn't stop. Common with JVM GC pauses — GC freezes the world, lease expires, GC completes, leader continues as if nothing happened.

Client-Side Caching

Clients cache the old leader's address and keep sending writes after the election. No fencing check = writes accepted by demoted node.

Missing Storage Fencing

Fencing tokens generated but storage layer doesn't check them. All the ceremony of fencing, none of the protection.

07
Practical Design Rules
1
Use existing consensus implementations. Don't hand-roll Raft or Paxos for production. etcd, Consul, ZooKeeper exist for this reason.
2
Tie leadership to term/epoch and ENFORCE on every write. Storage must reject operations from stale leaders. Not optional.
3
Make lease timeouts conservative relative to network and GC pauses. Aggressive timeouts = unnecessary failovers. Long GC pauses in JVM = classic footgun.
4
Distinguish leader-side failure detection from client-side routing. Clients should not invent their own idea of who the leader is based on timeouts.
5
TEST partition behavior explicitly. Chaos experiments. Unit tests will not catch split-brain scenarios. You need to actually partition the network.
6
Observe leadership changes. Track metrics for: leader transitions, election duration, lease renewals, rejected fencing tokens. Alert on unexpected patterns.

Quick Reference
⚡ Leader Election Cheat Sheet
Safety (non-negotiable) AT MOST ONE leader per term. Two simultaneous leaders = split-brain = data loss.
Raft terms Logical clocks. Higher term always wins. One vote per node per term. Majority required.
Lease-based critical rule Stop work when lease MIGHT have expired, not when you notice loss. Violating this = split-brain.
Fencing tokens Every write carries the current epoch. Storage rejects writes with stale epoch. Non-negotiable.
JVM GC footgun Long GC pauses can exceed lease timeout. Leader thinks it's alive; it isn't. Set conservative timeouts.
Chaos test Unit tests won't find split-brain. Must actually partition the network in integration tests.
Don't hand-roll Use etcd, Consul, ZooKeeper, or K8s lease API. Distributed consensus is subtle and brutal.
Observability Track: leader transitions, election duration, lease renewals, rejected fencing tokens.
When election is wrong tool Stateless work, leaderless replication, simple mutual exclusion → distributed lock may suffice.
