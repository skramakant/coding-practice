Back-of-the-Envelope Estimation

"Back-of-the-envelope estimation is how experienced engineers avoid building the wrong system. Ten minutes with a whiteboard rules out half the proposed architectures."

01
Why It Matters
The Whiteboard Ritual at Large Tech Companies

Before any serious design discussion, someone writes numbers on the whiteboard: requests per second? Data per day? Machine disk size? Network round trip latency?

Ten minutes later, half the proposed architectures are already ruled out. Not ideology or preference — the arithmetic doesn't work.

Definition

Back-of-the-envelope = Fermi estimation applied to software. Approximate important quantities using orders of magnitude, known constants, simple multiplication. Goal: within 10x (not 5%). Often enough to reject a design or choose between options.

Typical Questions It Answers

  • Can this fit on one machine?
  • Need sharding on day one?
  • Is the bandwidth bill absurd?
  • Is latency budget spent before writing code?
  • How many machines at peak load?

What It Is NOT

  • Not a substitute for load testing
  • Not precise forecasting for finance
  • Not an excuse to ignore measurement once system exists
  • It's a FILTER — removes impossible and absurd designs early

Key Formula

QPS ≈ (DAU × actions per user) / seconds per day

DAU = daily active users. Use 10⁵ for seconds per day. Round everything aggressively.

A Simple 6-Step Process
1
Clarify what you're estimating. QPS? Storage after 5 years? Bandwidth? Number of machines? Be explicit — different metrics need different inputs.
2
Identify the drivers. User count, event size, retention period, replication factor, peak-to-average ratio. List them explicitly before multiplying.
3
Use round numbers. 10M users, not 9.4M. 1KB per event, not 874 bytes. Round numbers compound cleanly and reveal the order of magnitude clearly.
4
Work in orders of magnitude first. Is this a 10³, 10⁶, or 10⁹ problem? Get the exponent right before worrying about the coefficient.
5
Sanity-check against known systems. More write QPS than a single Postgres primary can handle? More storage than a typical shard? More network than a 10Gbps link?
6
Call out soft spots explicitly. "If average image size is 2MB instead of 200KB, storage is 10x higher." Make assumptions visible so they can be challenged.

When Estimates Change the Design

📊 Latency Budgets

If you need 100ms p99 and one cross-region call is 150ms, that call cannot be on the critical path. Forces caching, regionalization, or async — revealed by estimation before any code is written.

💾 Storage Growth

Logging 5KB/event at 50k events/sec = ~20GB/hour = ~500GB/day = ~180TB/year before compression. Retention and sampling stop being abstract — they become cost controls.

🔗 Connection Limits

10k concurrent connections per machine is a common soft limit. If the estimate requires 100k connections, you need more machines or a different protocol — not discovered through intuition alone.

07
Traps to Avoid
⚠ False Precision

"1,247 shards" derived from soft inputs is theater. Prefer "hundreds of shards" until the inputs are firmer. Precision implies confidence that doesn't exist.

⚠ Ignoring Peaks

Average QPS is NOT what breaks systems. Peak concurrent users, peak write bursts, thundering herds are. Always estimate peak, not just average.

💀 Forgetting Amplification

Replication (3x), indexes (2x), secondary storage, temporary objects, retries — all multiply the base number. 1TB becomes 6TB quickly. Always apply amplification factors.

💀 Not Writing Assumptions Down

If assumptions are invisible, nobody can challenge them and the estimate can't be updated with better data. Write every assumption explicitly before calculating.

💡 The Takeaway

"Back-of-the-envelope estimation is how experienced engineers avoid building the wrong system. Learn a few constants. Practice multiplying them under time pressure. Force every non-trivial design through a quick capacity and latency check before committing to it."
