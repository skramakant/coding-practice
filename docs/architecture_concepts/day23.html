Idempotency + Data Locality

"Two ideas that look small on a whiteboard and dominate real incident reports. Miss either one and you get duplicate charges, thundering herds, and multi-second latencies."

01
Why These Two?

Idempotency

Networks fail. Clients retry. Message queues deliver at-least-once. Load balancers replay requests. Without idempotency, every retry is a potential double charge, double email, double inventory decrement.

Turns at-least-once delivery into effectively-once behavior — without expensive exactly-once infrastructure.

Data Locality

The fastest network call is the one you never make. Every cross-node, cross-AZ, or cross-region hop adds latency, failure modes, and coordination cost.

Data locality = practice of placing data where the computation (or user) already is.
Production Reality

Neither idea is glamorous. Both are visible in almost every serious post-mortem involving money, inventory, or multi-region traffic. They look small on a whiteboard and dominate real incident reports.

02
Idempotency — Making Retries Safe
Definition

An operation is idempotent if performing it multiple times produces the same result as performing it once. SET balance = 500 is idempotent. INCREMENT balance BY 10 is not.

✅ Natural Idempotent Operations

  • PUT /resource with full state representation
  • SET balance = 500 (absolute assignment)
  • INSERT ... ON CONFLICT DO NOTHING
  • INSERT ... ON CONFLICT DO UPDATE
  • Idempotency key lookup + return stored result

❌ Dangerous Non-Idempotent Operations

  • DEBIT account BY 50 (relative change)
  • INCREMENT inventory by 1 without unique constraint
  • APPEND item to list without deduplication
  • POST /charges without idempotency key
  • Send email without tracking send status
⚠ Exactly-Once is a Myth at Scale

Exactly-once semantics require distributed transactions or heavy coordinator protocols. The overhead is almost never worth it. The correct pattern is: at-least-once delivery + idempotent consumers. This gives you effectively-once behavior at a fraction of the cost.

How to Implement Idempotency
1
Idempotency keys. Client generates a unique UUID for each logical operation and sends it with the request. Server stores key + result. On duplicate key, return the stored result instead of re-executing the handler.
2
Use naturally idempotent operations. PUT /resource with full state. SET balance = 500. INSERT ... ON CONFLICT DO NOTHING / DO UPDATE. Avoid "increment by 1" or "append this item" without a key or unique constraint.
3
Database constraints as last line of defense. Unique indexes on (user_id, idempotency_key) or on business identifiers. Even if application logic forgets, the database rejects the duplicate.
4
At-least-once + idempotent > exactly-once. Exactly-once requires distributed transactions or heavy coordinator protocols. Almost always prefer at-least-once delivery with idempotent consumers — same outcome at a fraction of the complexity.

Production Checklist

✓ Every payment, order creation, email send, and inventory mutation has an idempotency key or unique constraint
✓ Retries from clients, queues, and internal services all carry the same key — never generate a new key on retry
✓ Keys have TTL (e.g., 24–72 hours) so the idempotency store doesn't grow forever
✓ Monitor "idempotency hit rate" — a sudden drop often means keys are not being propagated correctly
05
Data Locality — Making the Common Path Fast
Core Principle

The fastest network call is the one you never make. Every cross-node, cross-AZ, or cross-region hop adds latency, failure modes, and coordination cost. Data locality = placing data where the computation or user already is.

1. Compute Close to Data

Run analytics jobs on the same machines that hold the data (Spark, BigQuery). Avoid "pull everything to a central service then process" — the network transfer dominates.

2. Data Close to Users

Geo-replicate or cache popular data in the region where users are. CDN for static assets. Regional read replicas. Edge caches. Intercontinental round trips are 100–300ms per hop.

3. Co-locate Related Data

In a sharded system, put a user's orders + profile + preferences on the same shard (shard by user_id). Cross-shard joins and transactions become rare instead of routine.

4. Session/Request Locality

Sticky sessions or consistent hashing so repeated requests from the same user hit the same cache or replica with data already warm. Avoids cold-start penalty on every request.

06
Data Locality: Co-location vs Remote
⚠ Common Locality Mistakes
  • Sharding by random key and doing frequent cross-shard queries
  • Putting cache in a different region from the application
  • Running global secondary indexes that force every write to touch multiple regions
  • Chatty microservices where one user request fans out to 15 services in different AZs
07
Combining Both Ideas — Practical Rules
1
Make the write path idempotent first. Then you can safely retry, timeout aggressively, and use at-least-once queues without fear. Idempotency is the enabler of reliable retry logic.
2
Design data model for locality before service boundaries. If the most common transaction touches data in 3 different services, the service boundaries are probably wrong. Fix the data model, then the boundaries follow.
3
Prefer "process locally, propagate asynchronously." Local decision + eventual reconciliation is almost always faster and more available than a distributed transaction. The coordination overhead of synchronous cross-region writes is prohibitive.
4
Measure cost of non-locality. Track cross-AZ and cross-region traffic. When it spikes, you have a locality problem — often long before users complain about latency. Instrument this from day one.
5
Idempotency keys must travel with the request. Through API gateway, message queues, internal RPCs — every hop. If any single hop drops the key, the guarantee is gone. Propagation is not optional.
Without These Patterns With Idempotency + Locality
Retry = double charge risk Retry = safe, returns same result
Every retry = potential duplicate side-effect At-least-once queues are safe to use
Shard by random key = cross-shard joins on every query Shard by user_id = single-shard reads for common case
Cache in wrong region = cross-AZ hops on every request Cache co-located with app = sub-millisecond lookup
Chatty services = 15 AZ hops = latency stacking Local decisions + async propagation = fast + available
Distributed transactions for consistency Local consistency + async reconciliation at a fraction of the cost

💡 Series Finale Takeaway

"Idempotency makes retries safe. Data locality makes the common path fast and cheap. Together they remove entire categories of production pain: duplicate side-effects, latency spikes from unnecessary network hops, cascading failures from chatty non-local architectures, and the need for heavy distributed transactions."

"Build them in from the start. They are far cheaper to design for than to retrofit after the incidents start arriving."
