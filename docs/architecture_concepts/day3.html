Caching — 5 Layers

From browser to hardware — every layer that stands between your users and your database, with latency numbers attached.

Source: 25-Day Scaling & Architecture Series

1 The 5 Cache Layers

Ordered from closest to the user (fastest, cheapest) to closest to hardware (slowest to reach, but huge impact when effective).

1
Browser Cache
Cache-Control headers tell the browser how long to keep a resource. Version filenames (app-v2.5.js) allow aggressive caching — when code changes, filename changes, cache busted automatically.
0 ms
2
CDN Edge Cache
Regional servers cache content near users. Key benefit: thousands of users share a single origin fill — if 1,000 users in Singapore hit the same asset, origin serves it once and all 1,000 get the cached version.
5-20 ms
3
Application Cache (Redis / Memcached)
In-memory cache sitting between your application and database. Uses the cache-aside pattern: check cache first, hit returns immediately, miss fetches from DB, stores in cache, returns. Transforms 20-100ms DB queries into 1-5ms cache reads.
1-5 ms
4
Database Query Cache
DB-internal caching of query results. Note: MySQL removed its query cache in v8.0 (it was a bottleneck). PostgreSQL uses prepared statements and shared buffers instead. Don't rely on this layer — use application-level caching instead.
~20-100 ms
5
OS Page Cache
The OS automatically caches frequently read disk blocks in RAM — no configuration required. When your entire database fits in RAM, disk reads are served from this cache at near-memory speed. This is why more RAM helps a database more than more CPU.
~0-5 ms
if in RAM
💡 OS Page Cache Insight

If your entire database fits in RAM, every query is essentially a memory read. This is why adding RAM to a database server often improves performance dramatically — the OS page cache does the work for you without any code changes.

3 Cache-Aside Pattern (Read Path)

The most common caching pattern. Application code controls what gets cached and when.

1️⃣
Check Redis
App checks cache for key before going to DB
✅
Cache Hit
Key found → return immediately. 1-5ms done.
❌
Cache Miss
Not found → query DB (20-100ms)
💾
Store & Return
Store in Redis with TTL, return to caller. Next request is a hit.

4 Redis vs Memcached

Feature Redis Memcached
Data structures Strings, hashes, lists, sets, sorted sets, streams, geospatial Strings only (key-value)
Threading model Single-threaded (mostly) + I/O threads Multi-threaded natively
Persistence RDB snapshots + AOF log None — memory only
Replication Master-replica built-in No built-in replication
Pub/Sub Yes — built in No
Best for Rich data structures, sessions, leaderboards, pub/sub Simple, ultra-high-throughput key-value caching
💡 Rule of Thumb

Pick Redis by default (95% of use cases). Choose Memcached only when you need maximum multi-threaded throughput for pure string caching with no other features needed.

5 When NOT to Use Redis

Avoid Redis caching when:

🔄 Data changes every request

Cache TTL expires before any hit. You're paying cache overhead with zero benefit.

📦 Very large objects

Redis is in-memory. Caching 50MB objects burns expensive RAM. Serialize to smaller representations or don't cache.

💰 Staleness = lost money

Inventory counts, financial balances, real-time pricing. A stale cache causes business harm.

6 Quick Reference

📋 Caching Cheat Sheet
Static assets (JS, CSS, images) Browser Cache + CDN. Use versioned filenames.
API responses (same for everyone) CDN edge cache. Set appropriate TTL.
Expensive computed results Redis (cache-aside). Cache on first request, TTL based on freshness needs.
User sessions Redis. Fast reads, rich data structure support.
Leaderboards / rankings Redis sorted sets. Native O(log N) operations.
Simple string-only, max throughput Memcached over Redis.
DB in RAM fully OS page cache handles most reads. Add RAM before CPU.
MySQL query cache Removed in 8.0. Don't rely on it. Use app-level cache.
Cache-aside miss latency 1-5ms Redis hit vs 20-100ms DB query.
