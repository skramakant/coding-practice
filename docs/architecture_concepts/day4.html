Cache Invalidation

One of the two hard problems in computer science. The core challenge: your DB has truth, your cache has a copy, and every write makes that copy a liar.

Source: 25-Day Scaling & Architecture Series

1 The Core Problem

Your database is the source of truth. Your cache is a copy. The moment you write to the database without updating the cache, the cache becomes a liar — serving stale data to users as if it were fresh.

The challenge: you need a strategy for every write operation that keeps cache and database consistent, while minimizing the performance penalty of doing so.

2 Three Write Strategies

1️⃣

Write-Through

Consistent

Write to BOTH DB and cache simultaneously on every write operation. Cache is always up to date because it's updated on every write.

✅ Pros

  • Always consistent
  • No stale reads after writes
  • Simple reasoning

❌ Cons

  • Slower writes (two systems)
  • Both can fail partially
  • Caches rarely-read data (wasted space)
2️⃣

Write-Behind (Write-Back)

Risky

Write to CACHE first, DB updated later in background asynchronously. The fastest write path possible — just one in-memory write.

✅ Pros

  • Insanely fast writes
  • Reduces DB write pressure
  • Can batch multiple writes

❌ Cons

  • Redis crash = DATA GONE
  • Complex failure recovery
  • Async lag can cause issues
🚨 Never Use For

Financial transactions, order data, payment records — anything where lost writes cause real-world harm. If Redis crashes before flushing to DB, that data is permanently gone.

3️⃣

Write-Around (Cache-Aside)

Recommended default

Write to DB only. Cache is updated on the next read (cache miss). Simple, no wasted cache space for data that may never be re-read.

✅ Pros

  • Simple to implement
  • No wasted cache space
  • Cache fills on demand

❌ Cons

  • First read after write = cache miss
  • Cold-start latency spike
✅ Recommended for 80% of use cases

Write-around (cache-aside) with explicit key deletion on write. It's simple, safe, and avoids race conditions. The first read after a write pays the DB latency cost — that's usually acceptable.

3 Write Strategy Flow Diagrams

4 Cache-Aside with Explicit Invalidation

The recommended pattern for 80% of use cases combines write-around with an important twist: on every write, DELETE the cache key instead of updating it.

❌ Don't: Update cache on write

// Race condition risk!
db.update(user)
cache.set("user:1", data) // wrong

✅ Do: Delete cache key on write

// Safe and simple
db.update(user)
cache.del("user:1") // correct

Why DELETE instead of UPDATE? If two writes happen concurrently, an update can write stale data into the cache. A delete forces the next read to fetch fresh data from DB — no race condition possible.

5 Cache Expiry Approaches

⏰ TTL-Based (Time-to-Live)

Set a time limit on cached data. Cache expires automatically — "set and forget." You accept some staleness window.

  • Zero infrastructure overhead
  • Always eventually consistent
  • Staleness window = TTL duration
  • Best for: product listings, content, most data

⚡ Event-Driven (Immediate)

Cache is invalidated immediately when data changes via events (Kafka, CDC — Change Data Capture). Near-zero staleness window.

  • Near-real-time consistency
  • Requires event infrastructure (Kafka/CDC)
  • Higher operational complexity
  • Best for: inventory, pricing, permissions

6 Decision Cheat Sheet

📋 Cache Invalidation Decision Framework
Product listings / content Write-around + TTL. Simple, staleness acceptable.
User sessions / auth tokens Write-through + TTL. Must be consistent.
Analytics / metrics Write-behind + TTL. Fastest writes, some loss acceptable.
Inventory / pricing Write-through + Event-driven. Stale = business harm.
Permissions / access control Write-through + Event-driven. Stale = security risk.
Financial transactions Never write-behind. Write-through or skip cache.
Default recommendation Write-around + explicit DELETE on write (80% of cases).
Avoid UPDATE on write Race conditions. Always DELETE the key, let next read fill.
Need real-time cache updates Add Kafka/CDC pipeline for event-driven invalidation.
