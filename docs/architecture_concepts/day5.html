Rate Limiting

Enforcing capacity limits before your system fails. Not a security tool — a reliability tool that buys you time.

Source: 25-Day Scaling & Architecture Series

1 Why Rate Limiting Exists

🔥 Real Incident

An internal batch job hit their own API: 400,000 requests in 90 seconds. No rate limiting was in place. Result: 10-minute outage. The attacker was themselves.

Rate limiting = enforcing a capacity limit BEFORE the system fails.

Without it, any client — external attacker, buggy internal service, or a well-intentioned batch job — can accidentally overwhelm your infrastructure. Rate limiting says "slow down" before you say "I'm down."

⚠️ Critical Clarification

Rate limiting is NOT a security solution. It does not prevent attacks. It buys time — it slows attackers down and prevents accidental self-inflicted overload. You still need proper security controls separately.

2 Three Rate Limiting Algorithms

🪣

Token Bucket

AWS, Stripe

A bucket holds N tokens. Each request consumes a token. The bucket refills at a constant rate (e.g., 10 tokens/second). If the bucket is full, new tokens are discarded. If empty, requests are rejected.

Key property
Allows burst traffic up to bucket size. If you have 100 tokens saved, a burst of 100 requests gets through instantly.
Best for
APIs with natural traffic bursts. Public APIs, search endpoints, most general use cases.
🪟

Sliding Window

Strict

Counts requests in a rolling time window (e.g., last 60 seconds). Each new request checks if the count in the past N seconds exceeds the limit. No burst allowance — just a strict per-window count.

Key property
Strict, no burst. Every window is identical. Prevents gaming fixed-window resets.
Best for
Auth endpoints (login), payment APIs, anything where burst exploitation is a risk.
🚰

Leaky Bucket

Smooth output

Requests enter a queue (the "bucket"). The queue drains at a constant rate — like water dripping from a leaky bucket. Extra requests beyond queue capacity are dropped.

Key property
Perfectly smooth output regardless of input burst. Downstream always sees constant rate.
Best for
Rate-sensitive downstream services (third-party APIs, video encoding, heavy export jobs).

4 4 Layers of Rate Limiting

Rate limiting is applied at multiple levels — each layer has a different scope and granularity. Apply all four for complete protection.

🌐
Layer 1 — API Gateway (Global)
Widest net. Limits total RPS across all users. Protects infrastructure from global floods. Managed at the gateway (Kong, AWS API Gateway, Nginx).
⚙️
Layer 2 — Per-Service Limits
Each microservice enforces its own limits independently. Prevents one slow service from consuming all capacity via a single entry point.
👤
Layer 3 — Per-User Limits
Fair usage enforcement. Implements pricing tiers (free: 100 RPM, pro: 1,000 RPM, enterprise: unlimited). Prevents one user from starving others.
🔗
Layer 4 — Per-Endpoint Limits
Different endpoints have different costs. Login endpoint: 5/min. Search: 30/sec. Heavy export: 2 concurrent. Matches rate to endpoint cost.
⚠️ Don't Rate Limit Health Checks!

Your load balancer polls health check endpoints at high frequency. If you rate limit /health or /ping, the LB will mark your instance as unhealthy. Explicitly exclude health check paths from rate limiting rules.

5 Proper 429 Response Format

When rate limiting, always return 429 Too Many Requests with informative headers so clients can self-throttle intelligently.

HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 100 ← Your total allowed requests
X-RateLimit-Remaining: 0 ← Requests left in window
Retry-After: 45 ← Seconds until window resets
X-RateLimit-Reset: 1735920000 ← Unix timestamp of reset

A well-designed client reads Retry-After and waits exactly that long before retrying — preventing the retry storm described below.

6 The Retry Storm Problem

🚨 How Retry Storms Happen

System gets overloaded → returns 429s → ALL clients retry at the same time (same retry interval) → synchronized wave of retries → bigger surge → more 429s → loop. Rate limiting itself causes the overload.

Fix: Exponential Backoff + Jitter

❌ Naive retry (causes storm)

retry after: 1s
retry after: 1s
retry after: 1s
// All clients synchronized

✅ Exponential backoff + jitter

retry after: 1s + rand(0-0.5s)
retry after: 2s + rand(0-1s)
retry after: 4s + rand(0-2s)
// Desynchronized clients

The jitter (random delay) ensures clients are desynchronized. Even if 1,000 clients all get 429 at the same time, they retry at different moments, spreading the load.

7 Implementation Notes

💾 Where to Store Counters

Multi-instance

Use Redis. Counters are shared across all instances. Atomic INCR + EXPIRE operations. Rate limit state is consistent regardless of which server handles the request.

Single instance

In-memory is fine. Faster, simpler. Only valid if you truly have one server and no plans to scale horizontally.

📊 How to Set Limits

1. Measure first — baseline normal traffic patterns
2. Set above normal, below breaking — limits should not trigger during normal use
3. Start lenient — tighten based on data, don't guess upfront
4. Monitor 429 rate — above 1-2% = investigate, limits too tight or abuse occurring

8 Quick Reference

📋 Rate Limiting Decision Cheat Sheet
Public API (general) Token bucket — 100 requests/min. Allows natural bursts.
Login / auth endpoint Sliding window — 5 attempts/min. Strict, no burst gaming.
Search endpoint Token bucket — 30 req/sec per user. Burst-friendly.
Heavy export / processing Leaky bucket — 2 concurrent. Smooth downstream load.
Multi-instance deployment Store counters in Redis. Atomic INCR operations.
Single server In-memory counters fine. Simpler and faster.
429 response must include X-RateLimit-Limit, X-RateLimit-Remaining, Retry-After
Prevent retry storms Exponential backoff + random jitter on client retries.
NEVER rate limit Health check endpoints (/health, /ping, /status)
Monitor threshold 429 rate above 1-2% → investigate root cause.
