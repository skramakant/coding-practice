API Gateway

The single entry point for all client traffic — your system's front door, bouncer, and translator rolled into one.

1 What Is an API Gateway?

An API Gateway is a single entry point for ALL client traffic. Without it, every microservice must independently implement auth, rate limiting, logging, CORS, input validation, and protocol translation — duplicating the same cross-cutting concerns across dozens of services.

💡 Core Idea

The gateway centralises all the boring but critical infrastructure concerns so your services can focus on business logic.

Without a Gateway — The Chaos

🔐 Auth duplicated

Every service validates JWT / API keys. One wrong implementation = security hole.

🚦 Rate limiting duplicated

Each service throttles independently. No aggregate view. Easy to bypass.

📋 Logging inconsistent

Every team logs differently. Debugging a request across services is a nightmare.

🔄 Protocol mismatches

External clients want REST. Internal services want gRPC. No place to translate.

2 The 6 Jobs of an API Gateway

🔐

1. Authentication & Authorization

Validates JWT tokens or API keys before the request ever reaches a backend service. One centralised auth layer — no service needs its own.

🚦

2. Rate Limiting

Enforces request limits per client/IP/API key. Connected to Day 5 concepts — token bucket, sliding window, etc. Protects all downstream services.

🗺️

3. Request Routing

Routes /api/users to the User Service, /api/orders to the Order Service. Path-based, header-based, or weighted routing.

🔄

4. Protocol Translation

External clients speak REST/HTTP. Internal services speak gRPC for efficiency. The gateway translates between protocols transparently.

⚡

5. Response Caching

Caches GET responses at the gateway edge. Repeated identical requests never hit the backend. Massive reduction in load for read-heavy endpoints.

📊

6. Logging & Observability

Every request logged in one place: latency, status codes, upstream service, user identity. Centralised traces without instrumenting every service.

3 Architecture Diagram

North-south traffic (external → system via Gateway) vs east-west traffic (service-to-service via Service Mesh).

4 Routing Patterns

📋 Header-Based Routing

API version in the request header routes to the correct service version:

X-API-Version: v1 → User Service v1
X-API-Version: v2 → User Service v2

Enables parallel running of multiple API versions with zero client disruption.

⚖️ Weighted Routing / Canary Deployments

Gradually shift traffic to a new version:

5% → new version (monitor)
25% → looks good, ramp up
100% → fully migrated

Rollback instantly if error rates spike.

🔀 Request Aggregation — BFF Pattern

Backend For Frontend (BFF): one call from mobile, gateway fans out to 3 services and returns one merged response.

Mobile → /api/dashboard
  ↳ GET /users/123
  ↳ GET /orders?user=123
  ↳ GET /notifications/123
  ← Merged JSON response

3 network calls → 1. Mobile clients love it.

5 API Gateway vs Service Mesh

💡 The One-Line Distinction

Gateway = north-south traffic (external clients INTO your system). Service mesh = east-west traffic (BETWEEN internal services).

Dimension API Gateway Service Mesh (Istio/Linkerd)
Traffic direction North-South East-West
Who talks to it External clients (browsers, apps, partners) Internal services talking to each other
Security Auth / rate limiting / API key validation mTLS between every service pair automatically
Reliability Basic retries, circuit breaking Advanced retries, circuit breaking, timeouts everywhere
Observability Access logs, latency per route Service-to-service tracing, per-call metrics
When to use Always — from day one At 20+ services for consistent security/observability
Common tools Kong, AWS API GW, NGINX, Traefik, Envoy Istio, Linkerd, Consul Connect
⚠️ At 5 Services

Handle retries and circuit breaking in application code. Service mesh overhead isn't worth it yet.

✅ Common Pattern at Scale

Use both layers: API Gateway for external traffic + Service Mesh for internal. They solve different problems.

6 Production Tips

🚫 Don't Build Your Own

Use battle-tested solutions: Kong, AWS API Gateway, NGINX, Envoy, Traefik. Building a gateway from scratch means you'll rediscover every edge case the hard way.

🚫 No Business Logic in Gateway

The gateway is infrastructure. Putting business logic there couples unrelated concerns and makes the gateway a deployment bottleneck. Services own their logic.

📌 Version APIs from Day One

Use /v1/users from the very first endpoint. Retrofitting versioning later is painful. You will need to break the API eventually.

❤️ Set Up Health Checks

Configure health checks through the gateway. It should actively probe services and stop routing to unhealthy instances automatically.

📈 Monitor the Gateway Itself

The gateway is your single point of entry. Track: p50/p95/p99 latency, error rate by route, downstream service health, rate limit hits. Run it in a cluster — not a single instance!

7 Decision Framework

Match your gateway complexity to your actual service count:

1
1 Backend Service → Simple reverse proxy (NGINX, Caddy). No gateway needed.
2–5
2–5 Services → Lightweight gateway (Traefik, NGINX Plus). Basic routing + auth.
10+
10+ Services → Proper gateway with canary, protocol translation, BFF aggregation (Kong, AWS API GW).
50+
50+ Services → Gateway + Service Mesh. Both layers. Non-negotiable at this scale.
