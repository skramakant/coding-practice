CAP Theorem

The most misquoted theorem in distributed systems. Understanding it correctly changes how you design every database choice.

1 The Famous Misquote

❌ Wrong — The Common Misquote

"Pick any 2 out of Consistency, Availability, and Partition Tolerance."

✅ Correct — What Brewer Actually Said

During a network partition, you must choose between Consistency and Availability. You cannot have both during the partition.

💡 Key Insight

You don't choose P. Network partitions WILL happen in any distributed system. Hardware fails. Network cables get cut. The real tradeoff: when a partition happens, do you choose C or A?

2 C, A, and P — Precisely Defined

C — Consistency

Every read returns the most recent write. All nodes in the cluster agree on the same data at all times.

If they can't agree?
They REFUSE the request rather than give you wrong information. A node that can't guarantee fresh data says "503, try again" — not lies.

A — Availability

Every request gets a response (though it may be slightly stale). Every node that is up will answer — without checking with other nodes first.

Trade-off:
The response may not reflect the very latest write. You might read data that's milliseconds or even seconds old.

P — Partition Tolerance

The system keeps working even when network communication between nodes is broken.

Why you always pick P:
No real distributed system can be "CA" (no partition tolerance). If you drop P, you have a single node — not a distributed system.

5 Real Systems — CP vs AP

System Type Behavior During Partition Use Case
Google Spanner CP Uses atomic clocks + GPS for globally consistent transactions. Refuses if can't confirm freshness. Financial data, global inventory
ZooKeeper CP Refuses reads if not the current leader. Used for distributed coordination and leader election. Config management, service discovery
etcd CP Raft consensus — won't serve stale reads. Used in Kubernetes for cluster state. K8s state store, distributed locks
Cassandra AP Last-write-wins conflict resolution. Every node answers. Tunable consistency levels. Time-series, IoT, high-write apps
DynamoDB (default) AP Eventual consistency by default. Strong consistency available per-request at extra cost. Shopping carts, session data, user prefs
DNS AP Serves cached IP for TTL duration even if the record was updated. Stale for minutes — that's fine. Domain resolution everywhere

6 CAP is Per-Feature, Not Per-System

The same e-commerce platform needs different CAP trade-offs for different features. This is the most practical insight from CAP theorem.

📦 Product Catalogue
AP

Slightly stale price? Fine. High availability matters more.

📊 Last Item Inventory
CP

Overselling = disaster. Refuse rather than oversell.

💳 Payment
CP

Double charge or wrong balance = catastrophic.

⭐ User Reviews
AP

Review showing 1 min later? Nobody cares.

🛒 Shopping Cart
AP + conflict resolution

Multi-device add? Merge both. Availability matters.

🎯 Interview Answer

"It depends on the feature. Let me walk through which parts of the system need strong consistency and which can tolerate eventual consistency." — This is the answer interviewers want to hear.

7 PACELC — The Full Picture

CAP only describes behavior during failures. PACELC extends it to include normal operation too.

Partition → Availability or Consistency   |   Else → Latency or Consistency

During Partition (CAP part)

Choose: C (refuse bad data) or A (serve stale data). This is what CAP covers — the failure mode.

Normal Operation (the E part)

Choose: Low Latency (async replication, fast writes) or Consistency (synchronous replication, slower but always fresh).

📋 CAP Theorem — Cheat Sheet
The Real Statement During a network partition, choose C or A. You can't have both.
Why you always pick P Network partitions WILL happen. You can't opt out of distributed system failures.
C = Consistency Every read gets the latest write. Refuses rather than giving stale data.
A = Availability Every node answers. May return slightly stale data. Never a hard error.
CP systems Banks, ZooKeeper, etcd, Google Spanner. Refusing > wrong data.
AP systems Cassandra, DynamoDB, DNS. Stale data is acceptable.
CAP is per-feature Same app: catalogue=AP, inventory=CP, payment=CP, reviews=AP.
