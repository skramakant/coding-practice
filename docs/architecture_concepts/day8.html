Database Sharding

Most teams reach for sharding when there are 4 cheaper things to try first. Know when — and when NOT — to shard.

1 Sharding vs Partitioning — Know the Difference

🗂️ Partitioning

Splitting a table into smaller pieces within ONE database server. Same server, same backups, same connection pool.

  • ✅ Low-risk and reversible
  • ✅ Same server — no distributed systems overhead
  • ✅ Backups still work the same way
  • ✅ JOINs and transactions work normally
  • ✅ Try this first — always

⚡ Sharding

Splitting data across MULTIPLE database servers. Each shard is a fully independent database.

  • ⚠️ Cross-shard queries are expensive
  • ❌ JOINs across shards don't work
  • ❌ Cross-shard transactions need distributed coordination
  • ❌ Rebalancing when adding shards is painful
  • ⚠️ Irreversible without major work
📏 Golden Rule

Partition before you shard. If partitioning solves the problem, you avoided months of distributed systems headaches. Sharding is a last resort, not a first step.

2 The 3 Sharding Strategies

📊 Range-Based Sharding

A-H → Shard 1
I-P → Shard 2
Q-Z → Shard 3
✅ Range queries fast ❌ Hotspots (all "S" names on shard 3)

Good for time-series data when hotspot risk is managed. Bad for names/IDs with skewed distribution.

🔢 Hash-Based Sharding

hash(user_id) % num_shards
→ shard index
✅ Even distribution ❌ Range queries destroyed ⚠️ Adding shard = rehashing

Most teams use this with consistent hashing to handle adding/removing shards without full reshuffling.

📖 Directory-Based Sharding

lookup_table[user_id]
→ shard_id
✅ Maximum flexibility ❌ Lookup table = SPOF ❌ Bottleneck at scale

Good when you need to remap data to shards without rehashing. Risky because the directory is a single point of failure.

4 Choosing a Shard Key — The Most Important Decision

🚫 Worst Mistake

Choosing a shard key that makes writes fast but reads require scatter-gather across all shards. Always optimize for reads — that's your hot path.

✅ Good Shard Key Properties

  • Shard on the most-queried field — the field you filter on most
  • High cardinality — thousands or millions of distinct values
  • Even distribution — no single value dominates (avoid status, boolean fields)
  • Co-locate related data — avoid cross-shard operations

❌ Bad Shard Key Examples

  • status — only a few values, huge hotspots
  • country — uneven (US gets 80% of data)
  • created_at alone — current day = hotspot
  • email_domain — gmail.com dominates everything

5 Common Shard Keys by Domain

Domain Shard Key Reasoning
Multi-tenant SaaS tenant_id All queries are per-tenant. Data naturally isolated. Easy customer-level scaling.
Social Network user_id Feeds, posts, connections all query by user. Co-locates user's data.
E-Commerce customer_id Orders, cart, wishlist all filter by customer. Keeps customer journey on one shard.
Time-Series / IoT time_bucket + hash Avoids current-time hotspot. Combines time range with even distribution.
Chat / Messaging conversation_id All messages in a conversation co-located. Efficient conversation fetching.

6 The 6-Step Escalation Ladder

Before reaching for sharding, exhaust these options in order:

1
Optimize Queries — Add missing indexes, rewrite slow queries with EXPLAIN, eliminate N+1 queries
2
Add Connection Pooling — PgBouncer, ProxySQL. Often eliminates connection exhaustion bottlenecks instantly
3
Add Read Replicas — Route read-heavy traffic to replicas. Cheap horizontal read scaling
4
Partition Large Tables — Range/Hash/List partitioning within the same DB. Low risk, high reward
5
Vertical Scaling — Bigger server: more RAM, faster SSD, more CPU. Often buys months of runway
6
Sharding — Only when ≥500 GB OR ≥10k writes/sec AND all above options exhausted

7 Quick Reference

📋 Sharding — Cheat Sheet
Partitioning vs Sharding Partition = same server. Shard = multiple servers. Partition first, always.
Range-Based A-H, I-P, Q-Z. Fast range queries. Risk: hotspots on popular ranges.
Hash-Based hash(key) % N. Even distribution. Range queries scan all shards. Use consistent hashing.
Directory-Based Lookup table → shard. Max flexibility. Lookup table = SPOF + bottleneck.
Best shard key properties High cardinality, even distribution, most-queried field, co-locates related data.
Worst mistake Shard key optimized for writes but reads require scatter-gather across all shards.
When to shard ≥500 GB or ≥10k writes/sec, after exhausting 5 other options.
Sharding adds complexity Cross-shard JOINs break. Transactions need distributed coordination. Rebalancing is painful.
By domain: SaaS tenant_id — Social: user_id — E-comm: customer_id — Chat: conversation_id
Consistent hashing Handles adding/removing shards without reshuffling all data. Use it.
