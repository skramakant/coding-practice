Database Replication

Keeping multiple copies of data on different machines — the foundation of durability, read scaling, and high availability.

1 What Is Replication & Why It Matters

Replication = keeping multiple copies of data on different machines. It's not just backup — it's the foundation of four critical capabilities:

🛡️ Hardware Failure

When a disk or server dies, another replica takes over. No data loss, minimal downtime.

📈 Read Scaling

Route read-heavy traffic to replicas. Offload 80%+ of queries from the primary.

🌍 Geographic Performance

Replica in Singapore serves Singapore users with low latency — no round-trip to US.

🔧 Zero-Downtime Maintenance

Promote replica to primary, do maintenance on old primary, rejoin as replica.

2 Synchronous vs Asynchronous vs Semi-Synchronous

🔒 Synchronous Replication

Leader waits for follower acknowledgment before confirming the write to the client.

✅ Strong consistency ✅ Zero data loss ❌ Slower writes ❌ Extra network RTT per write

If the sync follower goes down, writes block until it recovers or gets demoted to async.

⚡ Asynchronous Replication

Leader confirms write immediately to client, then sends changes to followers in background.

✅ Fast writes ✅ Follower failure doesn't block writes ❌ Data loss if leader dies before sync

Replicas are "eventually consistent" — lag can be milliseconds to seconds.

⚖️ Semi-Synchronous (Production Choice)

One follower synchronous (durability guarantee) + rest async (speed). Best of both worlds.

✅ Durability without full sync cost 💡 If sync follower dies, async promoted to sync

MySQL, PostgreSQL with Patroni, and most cloud RDS setups use this pattern.

4 Replication Lag & the Read-Your-Own-Writes Bug

⏱️ Replication Lag

Delay between a write hitting the leader and appearing on a replica.

  • Normal: milliseconds
  • Under load: seconds or even minutes
  • Alert threshold: consistently >1 second
SELECT now() - pg_last_xact_replay_timestamp()
→ Check replication lag in PostgreSQL

🐛 The Read-Your-Own-Writes Bug

Classic distributed bug scenario:

  1. User updates their profile photo ✅
  2. Page refreshes → reads from replica
  3. Replica hasn't caught up yet
  4. User sees old photo → thinks update failed
  5. User updates again → duplicate write
Fix

Route a user's own reads to the leader for a few seconds after they make a write. Sticky sessions or a "written at" timestamp in the user's session.

5 Failover — When the Leader Dies

1
Detect failure — followers detect missed heartbeats after a timeout (usually 30s–2min)
2
Election — the follower with the most up-to-date data (highest WAL position) becomes the new leader
3
Reconfigure — other followers start replicating from the new leader instead
4
DNS / connection pool updated — traffic redirected to new leader's address
5
App reconnects — applications reconnect through updated connection pool (PgBouncer absorbs the reconnection storm)
SetupFailover TimeNotes
AWS RDS Multi-AZ 30–120 seconds Managed automatic failover. DNS switch takes most of the time.
Patroni (well-configured) <10 seconds Open-source HA for PostgreSQL. Uses etcd/ZooKeeper for leader election.
Manual failover Minutes–hours Without automation, human response time dominates. Unacceptable for production.
⚠️ Connection Storms

After failover, all app instances try to reconnect simultaneously. A connection pooler (PgBouncer) absorbs the storm — the app connects to the pooler, and the pooler reconnects to the new leader just once.

✅ Action Item

Test your failover quarterly in staging with a runbook. The time to discover your failover is broken is NOT during a production incident at 3 AM.

6 Split Brain & Fencing

🧠 Split Brain

The old leader comes back from a network partition and thinks it's still the leader. Now you have TWO leaders accepting writes. Data diverges. Catastrophic.

🔒 Fix: FENCING

When a new leader is elected, revoke the old leader's ability to write before promoting the new one:

  • Kill the old leader's database process
  • Revoke network access (firewall rule)
  • Use a fencing token — old leader's writes get rejected

💀 STONITH

"Shoot The Other Node In The Head" — the charmingly named approach where you physically power off the old leader via IPMI/DRAC before assuming the new one is safe to write.

Brutal but effective. Used in high-stakes database clusters where correctness is paramount.

7 Replication Topologies

Topology How It Works Pros Cons Use When
Single Leader Multi-Follower One leader accepts writes, N followers serve reads Simple, well-understood, standard RDS setup Leader is write bottleneck, failover complexity Read-heavy apps. The default choice.
Multi-Leader Multiple leaders in different regions, each accept writes Low-latency writes from any region Complex conflict resolution, write-write conflicts Multi-region write-heavy apps
Leaderless / Dynamo-style Any node accepts reads/writes. Quorum-based consistency. No failover needed, tunable consistency Conflict resolution, more complex reads (W+R>N) High availability, can't have downtime (Cassandra, DynamoDB)
